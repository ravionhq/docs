The Ravion GitHub App scans your repository for project and pipeline config changes. It previews changes on pull requests and applies them when they reach the repository's default branch. You don't need a GitHub Actions workflow, a runner, or a `RAVION_API_KEY` repository secret for this integration.

## Get started

1. Connect your GitHub repository to your Ravion organization through the Ravion GitHub App, and grant the app access to the repository.
2. Create the project or pipeline in Ravion if it doesn't exist yet. The GitHub integration updates existing projects and pipelines; it doesn't create them from config files.
3. Pull its config with the [CLI](/cli/installation):

   ```bash
   ravion project config pull <project-id> --file ravion.yaml
   ravion pipeline config pull <pipeline-id> --file ravion-pipeline.yaml
   ```

   Use either command or both, depending on what you want to manage. Keep the `project` or `pipeline` block in the file: it identifies the resource to update.

4. Edit the file, commit it on a branch in the same repository, and open a pull request.
5. Review the app's plan, then merge into the default branch to apply the config changes.

## Which files are scanned?

Ravion recognizes these filenames in any directory, including nested directories in a monorepo:

| Filename pattern | Examples |
| --- | --- |
| `ravion.yaml` | `ravion.yaml`, `infra/ravion.yaml` |
| `<name>.ravion.yaml` | `shop.ravion.yaml` |
| `ravion.<name>.yaml` | `ravion.shop.yaml` |
| `ravion-pipeline.yaml` | `services/web/ravion-pipeline.yaml` |
| `<name>.ravion-pipeline.yaml` | `deploy.ravion-pipeline.yaml` |
| `ravion-pipeline.<name>.yaml` | `ravion-pipeline.deploy.yaml` |

All patterns accept `.yaml`, `.yml`, `.json`, `.jsonc`, and `.cue`. For example, use `ravion.jsonc`, `shop.ravion.cue`, or `ravion-pipeline.deploy.json`. Names are case-sensitive. Files named `pipeline.yaml` or `ravion.yaml.bak` are not scanned, and nothing inside a `.github` directory is scanned: a GitHub Actions workflow at `.github/workflows/ravion.yml` is left to GitHub.

The extension selects the parser. JSON must be valid JSON; JSONC also supports comments and trailing commas. CUE files can use definitions, expressions, and standard-library imports, but must evaluate to a concrete config object. Each CUE file is evaluated independently: sibling files, repository-local imports, and external CUE modules are not loaded.

All supported formats use the same validation and automation: pull requests receive a dry-run plan, and merges into the default branch apply the changes. Direct commits to the default branch also apply changes.

The filename makes a file eligible for scanning; its contents determine whether it is a project config or a pipeline config. Ravion compares the top-level fields against the two schemas. Project configs describe `project` and `environments`; pipeline configs describe `steps` and `variants`, with a `pipeline` block identifying their target. A pipeline config can therefore live in a file named `ravion.yaml`, although `ravion-pipeline.yaml` makes its purpose clearer.

Ravion plans or applies changed files, not every file on each push. It also checks other recognized, non-ignored config files for conflicting target references.

## Exclude files with .ravionignore

Create a `.ravionignore` file at the repository root to exclude config files from the GitHub App's scan. Ignored files are not planned, applied, or counted in conflicts. Use this for test fixtures or examples that reuse a real project's or pipeline's target reference.

```text .ravionignore
# Ignore test fixtures in any directory
testdata/
*.test.ravion.yaml

# Ignore one example config, relative to the repository root
/examples/ravion.yaml

# Ignore matching files, but keep one config in the scan
*.demo.ravion.jsonc
!production.demo.ravion.jsonc
```

Patterns follow `.gitignore` syntax:

- Blank lines and lines starting with `#` are ignored.
- A pattern without a leading or middle `/` matches at any depth. A leading or middle `/` anchors it to the repository root.
- A trailing `/` matches directories only, including the files inside them.
- `*`, `?`, `[...]`, and `**` are supported.
- `!` negates a pattern; the last matching rule wins. You cannot re-include a file while its parent directory is ignored. Re-include the directory first, or exclude individual files instead.
- Backslashes escape special characters, such as a leading `#` or `!`. Trailing spaces are trimmed unless escaped.

Only the root `.ravionignore` is read. A `.ravionignore` in a subdirectory has no effect. Ignore rules filter the supported config filenames; negation does not make an otherwise unrecognized filename eligible for scanning.

### Changing ignore rules

Ravion reads the `.ravionignore` from each commit. When GitHub returns complete repository trees, a change to this file alone can bring an unchanged config back into the scan: the app plans it on a pull request and applies it on the default branch. Ignoring one file of a conflicting pair also lets the remaining file be reconsidered.

<Note>
  If GitHub truncates a large repository tree, Ravion falls back to the changed-file list. In that case, changing only `.ravionignore` does not trigger a plan or apply for an unchanged config. The config is processed on its next edit, subject to the ignore rules.
</Note>

Ignoring a config does not delete its project, pipeline, or infrastructure. These rules control the GitHub App's automatic scan, not manual CLI plan or apply commands.

## How projects are matched

Ravion reads the top-level `project` block:

1. If `project.id` is present and non-empty, it takes precedence.
2. Otherwise, Ravion uses `project.givenId`.
3. The project must already exist in a Ravion organization connected to this repository. A project outside those organizations is treated as not found.

For example, this block targets a project by its unique ID:

```yaml
project:
  id: proj_3AV4cGr0t841Bstn4swCCrHrgly
  givenId: shop
  name: Shop
```

Without `id`, this block targets an existing project whose given ID is `shop`:

```yaml
project:
  givenId: shop
  name: Shop
```

These are identification blocks, not complete config files. Keep your `environments` and module configuration below them. Neither the filename, directory, repository name, nor `project.name` selects the project. An invalid `project.id` does not fall back to `project.givenId`.

Prefer the unique `proj_...` ID from a pulled config, especially when the repository is connected to multiple organizations that reuse the same given ID.

## How pipelines are matched

A standalone pipeline config must contain a top-level `pipeline` block. Ravion uses one of two forms:

- **Unique ID:** `pipeline.id` selects the existing pipeline directly and takes precedence over `pipeline.givenId`.
- **Given ID within a project:** when `pipeline.id` is absent or empty, both `pipeline.givenId` and `pipeline.project` are required. `pipeline.project` accepts the project's unique ID or given ID. Ravion finds that project first, then finds the pipeline by its given ID within that project.

For example, target a pipeline by its unique ID:

```yaml
pipeline:
  id: pipe_3AV4cGr0t841Bstn4swCCrHrgly
```

Or target the `deploy` pipeline in the `shop` project:

```yaml
pipeline:
  givenId: deploy
  project: shop
```

Keep `steps`, `variants`, and the rest of your pipeline config below the block. The given ID `deploy` alone is not enough: different projects can each have a pipeline with that given ID. If you also supply `pipeline.project` alongside `pipeline.id`, the project must match the pipeline's actual project.

The pipeline must belong to a connected Ravion organization; global system pipelines cannot be configured this way. The filename and `pipeline.name` do not select the pipeline, and an ID in a YAML comment is not a substitute for the `pipeline` block. Pull the current config to get that block rather than copying an old header comment.

## Pull requests and applies

### Preview on pull requests

When you open or reopen a pull request, push new commits, or mark it ready for review, the app dry-runs the changed configs against the current Ravion state. It maintains one plan comment, adds a summary to the pull request description, and reports a **Ravion config plan** check. Invalid configs fail the check.

Tick the re-plan checkbox in the app's plan comment to refresh the plan without pushing another commit. Pull requests from forks are not planned.

<Note>
  A config dry run previews configuration changes; it does not apply them or run a Terraform plan. Require **Ravion config plan** in your GitHub branch protection settings if you want a failed config plan to block merging.
</Note>

### Apply on the default branch

A push that changes a recognized config on the existing default branch applies it, whether the push comes from a merged pull request or a direct commit. Pushes to other branches do not apply configs.

- **Project configs** update the project configuration and start stack change pipeline runs when needed. Those runs create the Terraform plans.
- **Pipeline configs** are compared with the latest pipeline version. A changed config publishes a new version; an unchanged config does not create a version.

The app reports a **Ravion config apply** check and posts the apply result on the merged pull request when available.

<Warning>
  Applying a project config does not auto-approve infrastructure changes. The GitHub App leaves stack approval gates in place. Review and approve the Terraform plans in Ravion before the infrastructure changes apply. A successful config apply check does not mean those stack runs have finished.
</Warning>

## Conflicts and deleted files

Keep one non-ignored config file per project and one per standalone pipeline. When multiple recognized, non-ignored files name the same target reference, Ravion rejects those files together instead of choosing one. An unchanged file can conflict with a changed file. Remove the duplicate, change its target, or [exclude it with `.ravionignore`](#exclude-files-with-ravionignore) before merging. With complete repository trees, the remaining file is reconsidered when that conflict is resolved; see [Changing ignore rules](#changing-ignore-rules) for the large-repository fallback.

Deleting a config file does not delete its project, pipeline, or infrastructure. This differs from removing a module from a project config, which can plan a destroy. See [Project config file](/config-as-code/project-config-file).

## Replace an existing GitHub Actions workflow

If you previously installed a workflow to run `ravion project config apply` or `ravion pipeline config apply` on pull requests and merges:

1. Ensure each file uses a recognized filename and includes its target identification block.
2. Remove the old config plan/apply jobs so the workflow and app don't both apply the same change. Keep unrelated build, test, and deployment jobs.
3. Remove CLI-version update jobs, version files, and repository secrets only if no remaining workflow uses them.
4. If branch protection required the old workflow's plan check, replace it with **Ravion config plan**.

You can still use the CLI to preview or apply changes manually, or from other CI systems. See [Project config file](/config-as-code/project-config-file), [Pipeline config file](/config-as-code/pipeline-config-file), and [CLI authentication](/cli/authentication).
