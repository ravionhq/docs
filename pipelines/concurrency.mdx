Use `concurrency` on a trigger, step, or block to control competing runs that share its `key` and `scope`. Choose `cancel-intermediate` to replace work that has barely started while letting an older run finish:

```yaml
concurrency:
  value: 2
  behavior: cancel-intermediate
```

The first run starts immediately. When a newer run reaches the same concurrency limit, it can replace the oldest run if **both** conditions hold:

- The oldest run started less than **15 seconds** ago.
- Less than **30 seconds** have passed since the first run in that replacement chain started.

Run age starts when the pipeline workflow starts, not when an individual build step starts. Replacements inherit the original 30-second deadline; they do not restart it. Two runs are enough to trigger replacement, even if both would fit within the limit.

With `value: 2`, a quick burst behaves like this:

| Time | New run | Result |
| --- | --- | --- |
| 0 seconds | A | A starts immediately. |
| 6 seconds | B | B replaces A. |
| 12 seconds | C | C replaces B. |
| 18 seconds | D | D replaces C. |
| 24 seconds | E | E replaces D. |
| 30 seconds | F | The original deadline has passed. E stays; F starts when a slot opens. |
| 36 seconds | G | E stays; G replaces F. |

If B arrives when A is already 15 seconds old, A stays instead. After either deadline, the policy keeps the oldest run and the newest runs that fit the configured retention window, cancelling intermediate runs. With `value: 2` and no `queue_size`, that means the oldest and newest. Cancelled work still holds its slot until it stops.

Once a step with `cancellable: false` starts (built-in `deploy` and `terraform:apply` by default), neither cancelling behavior cancels that pipeline run. This protection does not detect publishing or infrastructure changes inside arbitrary shell commands; mark such steps `cancellable: false` yourself.

The replacement windows are part of `cancel-intermediate`; you do not need another setting. Other behaviors stay separate:

- `queue` waits for a slot without cancelling older runs.
- `skip` skips new work when the limit is reached.
- `cancel-in-progress` cancels older work without the age limits above. Both cancelling behaviors respect `cancellable: false` (below).
- `value: 0` allows unlimited concurrency and does not apply these cancellations.

## Shared holders

By default every holder of a key is `exclusive`: it takes one of the `value` slots. Set `mode: shared` on a step's `concurrency` to let it run alongside any number of other shared holders of the same key while still never running alongside an exclusive one. A shared run queues while an exclusive run holds the key, and an exclusive run queues until every shared holder has finished. Waiters are promoted in arrival order, so a queued exclusive run is never overtaken by shared runs that arrive after it.

With `value: 1` this is a reader/writer lock. Terraform plans only read state, so plans from different branches can run at the same time, while an apply needs the stack to itself:

```yaml
steps:
  - id: plan
    type: terraform:plan
    concurrency:
      key: <<pipeline.input.stack_id>>
      scope: organization
      value: 1
      mode: shared
  - id: apply
    type: terraform:apply
    concurrency:
      key: <<pipeline.input.stack_id>>
      scope: organization
      value: 1
```

## Steps that must not be cancelled

Set `cancellable: false` on a step's or block's `concurrency` to keep a run holding the key there from being cancelled by a newer run under `cancel-in-progress` or `cancel-intermediate`. The newer run queues behind it instead, and a cancellation that arrives after the step has started is refused. Manual cancellation still works. Built-in `deploy` and `terraform:apply` steps default to `cancellable: false`; every other step defaults to `true`.

Use this when steps that share a key are not equally safe to interrupt. The excerpt below shows only the concurrency fields; see [step types](/pipelines/step-types) for the rest of each step. A newer run's plan cancels an older run's plan on the same stack, but waits for an apply:

```yaml
steps:
  - id: plan
    type: terraform:plan
    concurrency:
      key: <<pipeline.input.stack_id>>
      scope: organization
      value: 1
      behavior: cancel-in-progress
  - id: apply
    type: terraform:apply
    concurrency:
      key: <<pipeline.input.stack_id>>
      scope: organization
      value: 1
      cancellable: false
```
