Use `concurrency` on a trigger, step, or block to control competing runs that share its `key` and `scope`. Choose `cancel-intermediate` to replace work that has barely started while letting an older run finish:

```yaml
concurrency:
  value: 2
  behavior: cancel-intermediate
```

The first run starts immediately. When a newer run reaches the same concurrency limit, it can replace the oldest run if **both** conditions hold:

- The oldest run started less than **15 seconds** ago.
- Less than **30 seconds** have passed since the first run in that replacement chain started.

Run age starts when the pipeline workflow starts, not when an individual build step starts. Replacements inherit the original 30-second deadline; they do not restart it. Two runs are enough to trigger replacement, even if both would fit within the limit.

With `value: 2`, a quick burst behaves like this:

| Time | New run | Result |
| --- | --- | --- |
| 0 seconds | A | A starts immediately. |
| 6 seconds | B | B replaces A. |
| 12 seconds | C | C replaces B. |
| 18 seconds | D | D replaces C. |
| 24 seconds | E | E replaces D. |
| 30 seconds | F | The original deadline has passed. E stays; F starts when a slot opens. |
| 36 seconds | G | E stays; G replaces F. |

If B arrives when A is already 15 seconds old, A stays instead. After either deadline, the policy keeps the oldest run and the newest runs that fit the configured retention window, cancelling intermediate runs. With `value: 2` and no `queue_size`, that means the oldest and newest. Cancelled work still holds its slot until it stops.

Once a built-in `deploy` or `terraform:apply` step starts, `cancel-intermediate` no longer cancels that pipeline run. This protection does not detect publishing or infrastructure changes inside arbitrary shell commands.

The replacement windows are part of `cancel-intermediate`; you do not need another setting. Other behaviors stay separate:

- `queue` waits for a slot without cancelling older runs.
- `skip` skips new work when the limit is reached.
- `cancel-in-progress` cancels older work without the age limits or deployment protection above. Add `cancel_only` to limit it to runs holding the key at the listed steps.
- `value: 0` allows unlimited concurrency and does not apply these cancellations.

## Cancel only some holders

`cancel_only` narrows `cancel-in-progress` to runs that hold the key at the listed steps. A run holding it at any other step is left alone, and the new run queues behind it. If the cancelled run has already moved past the listed steps when the cancellation arrives, it refuses it. Use this when steps that share a key are not equally safe to interrupt.

```yaml
steps:
  - id: plan
    type: terraform:plan
    concurrency:
      key: <<pipeline.input.stack_id>>
      scope: organization
      value: 1
      behavior: cancel-in-progress
      cancel_only: [plan]
  - id: apply
    type: terraform:apply
    concurrency:
      key: <<pipeline.input.stack_id>>
      scope: organization
      value: 1
```

Here a new run's plan cancels an older run that is still planning, but waits for an older run that is applying. Ravion's own stack pipelines use this.

See [ConcurrencyConfig](/pipelines/config-reference#concurrencyconfig) for `key`, `scope`, `queue_size`, and `cancel_only`. Deployment steps still use their separate deployment-manager lock.
