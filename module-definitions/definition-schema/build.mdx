### Pipeline.StepInfrastructure

Step infrastructure configuration, discriminated by `type`

Note: Additional validation via CEL:
- every infrastructure type needs exactly one target mode: execution_environment_id, or aws_account_id plus region
- an instance_size list must not mix x86_64 and ARM64 (Graviton) types
- a sandbox with disk_cache: auto needs a git source to name its disk by (a github:runner step names it by its job)
- a sandbox's cache_paths need disk_cache, and are clean absolute directories outside the guest's own

Discriminated union. The `type` field selects which schema applies.

<ResponseField name="disk" type="integer | auto">
  GiB of host disk the sandbox microVM may write — the restored lineage
  overlay plus everything the step builds before it is frozen. A host takes
  the sandbox only when it has this much free, and stops it if it writes
  more, failing the step with SandboxDiskExceeded, so a step that writes
  more than the default must say so. `auto` lets Ravion size it from earlier
  runs; requires `interruptible: true`.

  _(min:1; templateable)_
</ResponseField>

<ResponseField name="disk_cache" type="string | null">
  Whether the sandbox keeps its disk between runs, and which disk. `off`
  boots the pool's base image every run and keeps nothing. `auto` keeps the
  step's own disk, named by its git source and step (a GitHub runner job's
  by its repository, workflow and job), so it needs a git source. Any other
  value is a key: every step in the same execution environment that names
  the same key shares one disk, across repositories, pipelines and branches.
  The last green run to finish publishes it. Include repository or branch
  in the key when you want that separation. Explicit keys use the fixed
  `main` head with no branch fallback. Only `auto` restores from the run's
  branch, falling back to its base and default branches, and publishes to
  the run's branch. Keys are up to 200 lowercase letters, digits, ".",
  "_" or "-".

  _(minLen:1; templateable)_
</ResponseField>

<ResponseField name="cache_paths" type="string[] | null">
  Directories to keep with the build caches. A sandbox that keeps its disk
  keeps everything on it between runs. A new version of the pool's base
  image moves the disk onto the new image at its next run: the build caches
  go with it, and everything else starts again from the new image. A new
  major version of the base image starts the build caches again too. Docker's
  images, layers and volumes, the GitHub Actions tool cache and job
  workspaces, the checkout and the home directory `/root` are always kept.
  List another directory here when a step keeps a cache somewhere else,
  such as a tool under `/opt` or `/usr/local`. Up to 16 absolute
  directories, outside `/proc`, `/sys`, `/dev`, `/run`, `/tmp`,
  `/etc/ravion` and `/var/lib/ravion`.

  _(templateable)_
</ResponseField>

<ResponseField name="interruptible" type="boolean | null">
  Whether the step can be stopped partway and started over. Only an
  interruptible step can be placed on a spot host, and it is run again on
  another host if its host is lost or reclaimed. Leave it off for steps that
  change things outside the sandbox and can't safely be cut off and repeated,
  such as database migrations.

  _(templateable)_
</ResponseField>

<ResponseField name="execution_environment_overrides" type="Pipeline.ExecutionEnvironmentOverrides">
  Overrides for individual attributes of the resolved execution environment.
  A sandbox runs on a host of the environment's pool, so the host's network
  is the step's: a step whose overrides name another security group or
  subnet runs on a pool host launched into them, which is ended at its idle
  timer rather than kept. The whole block and each field inside it accept
  template tokens.

  See: [Pipeline.ExecutionEnvironmentOverrides](#pipeline-executionenvironmentoverrides)

  _(templateable)_
</ResponseField>

### Pipeline.ExecutionEnvironmentOverrides

Overrides applied on top of the resolved execution environment.

An execution environment is a saved network placement. These fields replace
individual attributes of whichever environment the step resolved — the one
named by `execution_environment_id`, the AWS account's default when none was
named, or the network selected from `aws_account_id` plus `region`. Every
attribute that is not overridden keeps the resolved value.

Replace semantics, not append: an overridden attribute is the only value
used. Overriding does not require naming an environment.

Both the block as a whole and each field inside it are templateable, so a
security group produced by an earlier step can be wired straight in.

<ResponseField name="security_group" type="string | null">
  Security group ID the runner is launched with, replacing the resolved
  execution environment's security group.

  _(minLen:1; templateable)_
</ResponseField>

<ResponseField name="subnet" type="string | null">
  Subnet ID the runner is launched into, replacing the resolved execution
  environment's subnet. It must be in the environment's VPC, or in the VPC
  `vpc` names.

  _(minLen:1; templateable)_
</ResponseField>

<ResponseField name="vpc" type="string | null">
  VPC ID the runner runs in, replacing the resolved execution environment's
  VPC. A subnet and a security group belong to one VPC, so a VPC other than
  the environment's is taken only with `subnet` and `security_group` naming
  a subnet and a security group in it.

  _(minLen:1; templateable)_
</ResponseField>
