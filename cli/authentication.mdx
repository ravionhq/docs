The Ravion CLI authenticates with your Ravion account and stores credentials locally for subsequent commands.

## Sign in

Sign in with:

```bash
ravion login
```

By default, `login` uses the device-authorization flow. The CLI prints a URL and a short code, and you approve the sign-in from any browser, including a browser on another device. This works on headless hosts.

## Check your identity

Confirm who you are signed in as:

```bash
ravion whoami
```

Add `--json` to get machine-readable output.

## Select an organization

If you belong to more than one organization, choose the active one:

```bash
ravion switch
```

This walks through your organizations and persists the selection. Pass `--org <id-or-name>` to skip the interactive picker. Switching organization clears the active workspace, so `ravion terraform` asks you to pick a workspace again.

## Sign out

Clear locally stored credentials:

```bash
ravion logout
```

## Credential storage

Credentials are stored under your config directory:

```text
${XDG_CONFIG_HOME:-$HOME/.config}/ravion/auth.json
```

## Service accounts and API keys

For CI and automation, use a service-account API key instead of a personal membership key or interactive login.

1. In the dashboard, open [**Settings / Service accounts**](https://app.ravion.com/org/settings/service-accounts).
2. Create or select the service account for your automation.
3. On that account's detail panel, click **Create API key** and copy the key.
4. Store it as your CI secret and pass it to the CLI as `RAVION_API_KEY`.

Create the key on the service account, not on your personal member profile.

### Create a key with the CLI

Use [CLI v1.16.8 or later](/cli/releases). Sign in as a user and select your organization:

```bash
unset RAVION_API_KEY
ravion login
ravion switch
```

Create or select a [service account](/cli/reference/service-account) with the permissions your automation needs. Key creation requires your user login; an existing API key cannot create another key.

For GitHub Actions jobs that use the CLI, run `gh auth login` and make sure your GitHub account can manage repository secrets. From your repository, replace `sa_YOUR_SERVICE_ACCOUNT_ID` with the service account's ID and pipe the new key directly into the [GitHub CLI](https://cli.github.com/):

```bash
set -o pipefail
gh auth status && \
  ravion api-key create --name "GitHub Actions" \
    --owner-type SERVICE_ACCOUNT --owner-id sa_YOUR_SERVICE_ACCOUNT_ID \
    --token-only | gh secret set RAVION_API_KEY
```

The token is returned only once. For other CI systems or without the GitHub CLI, run only `ravion api-key create` with the same flags and store its output in your secret manager as `RAVION_API_KEY`.

If transfer fails, find the unused key with `ravion api-key list`, delete it with `ravion api-key delete <key-id>`, and retry. Do not log or save the token to a file.

## Non-interactive authentication

Set a credential in the environment to authenticate without `ravion login`. When one of these variables is set, the CLI uses it instead of the stored credentials and skips the device-authorization flow.

| Variable | Description |
| --- | --- |
| `RAVION_API_KEY` | An organization-scoped service account API key. Takes precedence over the other variables and over any stored credentials. |
| `RAVION_TOKEN` | An OAuth access token. Used if `RAVION_API_KEY` is not set. |
| `RAVION_ACCESS_TOKEN` | Alias for `RAVION_TOKEN`. |

An API key is scoped to its organization, so you don't run `ravion switch` when you use `RAVION_API_KEY`. This is the recommended way to authenticate CLI commands in CI. The [Ravion GitHub App](/config-as-code/github-integration) plans and applies repository config changes without a CLI API key.

```bash
export RAVION_API_KEY=<your-api-key>
ravion whoami
```
