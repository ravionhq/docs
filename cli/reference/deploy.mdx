## `ravion deploy`

Deploy the app in this folder to an App Cluster.

ravion-app.yaml says how the app is built, started and served. `ravion deploy` reads it from the folder
or the nearest folder above it in the git repository, or from --file. A folder without one gets one
detected from its compose file or Dockerfile, written once you agree (--yes agrees in advance).

Every run asks for the App Cluster, listing the clusters of the ravion.yaml project at the repository
root first and taking the only one there is without asking, and for the app: one of the cluster's apps,
or a new one named after ravion-app.yaml. Nothing about the choice is written to the folder. Without
a terminal, in CI and with --yes or --json, pass --cluster and --app; --new refuses an app that exists.

An app's default branch is the branch of its first deploy. A deploy from any other branch goes to the app's
branch app of that branch, created by its first deploy and served at &lt;app&gt;--&lt;branch&gt;.&lt;domain&gt;, with a disk
and a deploy history of its own. --branch deploys as another branch than the one checked out.

The deploy uploads the git working tree, tracked files with their uncommitted changes (--include-untracked
adds new files .gitignore does not exclude), and a pipeline run builds the app, starts it and serves its
ports, while the deploy follows the run and streams its log. Variables that are not committed, such as
secrets, go with --env-file and --env.

Ctrl-C stops following; the run and the app keep going.

**Aliases:** `deploys`, `deployment`, `deployments`

```bash
ravion deploy [dir] [flags] [command]
```

**Examples:**

```bash
ravion deploy
ravion deploy ./services/api --cluster staging/apps --app api
ravion deploy --cluster shop/production/apps --app web --env-file .env --yes --json
```

**Flags:**

| Flag | Required | Description |
| --- | --- | --- |
| `--app <string>` |  | app to deploy to; a name no app on the cluster has creates it |
| `--branch <string>` |  | deploy as this branch in place of the one checked out: to the app from its default branch, else to the branch's branch app |
| `--cluster <string>` |  | App Cluster: minst_ id, &lt;environment&gt;/&lt;module&gt; in the ravion.yaml project, or &lt;project&gt;/&lt;environment&gt;/&lt;module&gt; |
| `--env <stringArray>` |  | variable KEY=VALUE for this deploy (repeatable); wins over --env-file |
| `--env-file <stringArray>` |  | file of KEY=VALUE lines for this deploy, such as a gitignored .env (repeatable) |
| `--file <string>` |  | the ravion-app.yaml to deploy, in place of the one found from the folder up |
| `--include-untracked` |  | also upload untracked files that .gitignore does not exclude |
| `--json` |  | emit response as JSON |
| `--new` |  | deploy only to a new app; refuse a name an app has |
| `-y, --yes` |  | never ask; write a detected ravion-app.yaml and fail when a choice is needed |

#### `ravion deploy resource rollback`

Roll an EKS workload's Helm release back

```bash
ravion deploy resource rollback <id> [flags]
```

**Flags:**

| Flag | Required | Description |
| --- | --- | --- |
| `--revision <helm rollback>` | yes | Helm's own revision number, from the release's history — not a Ravion identifier. Required and must be positive: helm rollback with no revision means "the previous one", and after a failed upgrade the previous revision and the last revision known to have WORKED are not the same one, so the caller has to say which it means.  It is validated against the revisions Ravion RECORDED for this module instance's prior successful deploys, and then again by the agent against Helm's actual in-cluster history. Both checks are needed and neither subsumes the other: the control plane cannot read a private cluster's release Secrets, and Helm prunes its history to `--max-history`, so a revision Ravion recorded may no longer be there to reinstate. |
| `--json` |  | emit response as JSON |
| `--operation-id <string>` |  | Stable idempotency identity. Reuse this value for every HTTP retry of the same user action; reusing it with changed input is rejected. |
| `--timeout-seconds <int>` |  | Seconds bounding the whole rollback, Helm's own wait included. Omitted takes the agent's default. Clamped on both ends. |

### `ravion deploy rollback`

Start a new deployment that replays a previous successful deployment. Choose the target with ravion deploy rollback-candidates &lt;deployment-id&gt;, then use ravion deploy wait &lt;new-deployment-id&gt; --watch with the new deployment ID returned by this command.

Requires a deployment ID (mdep_...), not a module instance ID (minst_...). Find deployment IDs with ravion deploy list --module-instance-id &lt;module-instance-id&gt;.

```bash

```

### `ravion deploy wait`

Wait for a deployment to finish, or to reach the status given by --until.

Use this instead of polling `ravion deploy get` in a loop. With --watch the command prints
status changes as they happen, then exits when the deployment is done. The command exits
non-zero when the deployment fails, is cancelled, or is rolled back.

```bash
ravion deploy wait <id> [flags]
```

**Examples:**

```bash
ravion deploy wait dep_123 --watch
ravion deploy wait dep_123 --watch --timeout 30m
ravion deploy wait dep_123 --until IN_PROGRESS --watch
```

**Flags:**

| Flag | Required | Description |
| --- | --- | --- |
| `--json` |  | emit response as JSON |
| `--timeout <duration>` |  | maximum time to wait; zero waits indefinitely |
| `--until <string>` |  | return when this status is reached, for example IN_PROGRESS |
| `--watch` |  | print deployment status changes while waiting |
