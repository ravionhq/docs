GitHub Actions workflows on Ravion can use three storage layers:

| Layer | Available on | Stores | Storage |
| --- | --- | --- | --- |
| Disk cache | Sandboxes only | The whole disk | S3 in your account |
| Actions cache | Sandboxes only | `actions/cache` and `setup-*` caching | S3 in your account |
| Artifacts | All Ravion runners | Workflow artifacts | GitHub |

On sandboxes, the disk cache usually makes path caches unnecessary; keep `actions/cache` steps if you also run the workflow elsewhere.

## Disk cache

On sandboxes, `disk_cache=auto` is the default. When a job ends, Ravion saves the sandbox's whole disk, and the job's next run starts with it: packages, installed tools, `node_modules`, Docker layers and your checkout. See [Why sandboxes are fast](/concepts/sandboxes#why-sandboxes-are-fast).

| Value | What it does |
| --- | --- |
| `auto` | Keep this job's own disk, named by its repository, workflow and job. |
| A key, such as `web-deps` | Share one disk across every job in the repository that uses the key. |
| `off` | Start from the base image every run. |

- With `auto`, a run restores the disk saved for its branch. If there's none, it uses the pull request's base branch, then the repository's default branch. It saves to its own branch.
- A run saves its disk when the job succeeds, or runs to its end and fails. A job that's canceled, loses its host, or writes past its `disk` limit saves nothing.
- On the default branch, only runs from triggers GitHub trusts for caches, such as `push`, `schedule` and `workflow_dispatch`, save. Runs from `pull_request_target`, `issue_comment` or `workflow_run` only read.
- A key shares one disk across branches, so only runs from those trusted triggers save to it, on any branch.
- A job with GitHub's `cache-mode: read` or `cache-mode: none` never saves its disk.
- Pull requests from forks never restore or save a disk.

## Actions cache

On sandboxes, `actions/cache` and actions that use the GitHub Actions cache API work without workflow changes. Ravion stores entries in the `actions-cache/` prefix of an S3 bucket in your account and keeps a hot copy on the host disk.

Cache reads try the job's branch, then the pull request's base branch, then the repository's default branch. Writes go to the job's own branch. On the default branch, only trusted triggers such as `push`, `schedule` and `workflow_dispatch` can write; other events can read only. Existing keys aren't overwritten.

GitHub's `cache-mode` controls whether a job restores or saves entries:

| `cache-mode` | What it does |
| --- | --- |
| `none` | Do not restore or save. |
| `read` | Restore entries but do not save. |
| `write` | Restore and save entries. This is the default. |
| `write-only` | Save entries without restoring them. |

Keys can be up to 512 characters. Entries can be up to 10 GiB and expire seven days after their last use. Restores are near-instant when the files are already on the restored disk.

Go builds use the same cache automatically through `GOCACHEPROG` unless you set your own.

Rust builds that use [sccache](https://github.com/mozilla/sccache) share the same cache too. Ravion sets `SCCACHE_WEBDAV_ENDPOINT` for every sandbox job, so jobs that already set `RUSTC_WRAPPER=sccache` get cache hits without changes. A cache backend set in your workflow, such as `SCCACHE_BUCKET` or `SCCACHE_GHA_ENABLED`, still takes precedence.

C and C++ builds that use [ccache](https://ccache.dev) 4.4 or later share the same cache. The sandbox image includes ccache, and Ravion points its remote storage at the cache for every sandbox job. Builds still have to call the compiler through ccache, for example with `CC="ccache gcc"` or CMake's `CMAKE_C_COMPILER_LAUNCHER=ccache`. A `remote_storage` or `secondary_storage` setting in your `ccache.conf`, or a `CCACHE_REMOTE_STORAGE`, `CCACHE_SECONDARY_STORAGE` or `CCACHE_CONFIGPATH2` variable, still takes precedence.

[Gradle](https://docs.gradle.org/current/userguide/build_cache.html) builds that enable the build cache, with `--build-cache` or `org.gradle.caching=true`, share the same cache. Ravion adds it as the remote build cache unless your settings already configure one. Builds that don't enable the build cache are unchanged.

[Turborepo](https://turborepo.com/docs/core-concepts/remote-caching) builds share the same cache without workflow changes. Ravion sets `TURBO_API` and `TURBO_TOKEN` for every sandbox job, so `turbo run` reports `Remote caching enabled` and replays task outputs that another job, branch or fresh disk already built. In `turbo.json`, declare every file a task creates in its `outputs`, because a cache hit restores only declared outputs. Also declare every environment variable that changes a task's result in its `env`, and any file outside the package in its `inputs`, because Turborepo leaves undeclared ones out of the cache key and could replay output built with different settings. A `TURBO_API`, `TURBO_TOKEN` or `TURBO_TEAM` set in your workflow still takes precedence, so a Vercel Remote Cache keeps working. To keep a job on its local cache only, run `turbo run --cache=local:rw`.

[Bazel](https://bazel.build/remote/caching) builds share the same cache without workflow changes. The sandbox image includes Bazelisk as `bazel`, which runs the Bazel version in your `.bazelversion`, and Ravion adds the cache to every `bazel build`, `test`, `run` and `coverage`. Bazel still downloads every output, so later steps find the same files in `bazel-bin` as without a cache. Ravion leaves Bazel alone when your workspace already sets a remote cache or a remote executor, in `.bazelrc`, its imports, `~/.bazelrc` or on the command line. To turn it off for a job, set `RAVION_BAZEL_CACHE=off`.

If the cache is unreachable, these tools build without it. Nx remote caches aren't filled in.

Pipeline sandbox steps with a git source use the same cache for Go, Rust, Turborepo and Bazel builds; see [shared build cache for pipeline steps](/concepts/sandboxes#shared-build-cache-for-pipeline-steps).

Public repositories get a separate cache per repository and can't read private caches. EC2 runners use GitHub's cache.

## Artifacts

Artifacts work on all Ravion runners. Use `actions/upload-artifact` and `actions/download-artifact` as usual. GitHub stores the artifacts, and its retention and limits apply. Ravion stores nothing.

If a sandbox job is rerun after its host is lost, Ravion replaces an artifact uploaded by the earlier attempt of that same job so the rerun's upload succeeds. Other artifact name conflicts are unchanged.
