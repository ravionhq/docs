This page covers jobs that run on sandboxes (`type=sandbox`). It explains where a job's AWS credentials come from, how its Docker containers get them, and how to use your own roles.

## How sandbox jobs get AWS credentials

Each job runs in its own Firecracker microVM. For each job, Ravion creates an IAM role in your execution environment's AWS account. The role's name starts with `rvn-ci-`, and its path is `/rvn-ci/`.

The sandbox host assumes that role with AWS STS and serves the credentials inside the microVM at the standard instance metadata endpoint, `169.254.169.254`. The paths match EC2's instance metadata service (IMDS). Each STS session lasts 15 minutes, and Ravion refreshes it automatically for as long as the job runs.

The AWS CLI and AWS SDKs find these credentials with no setup, in `run` steps and in the job's [Docker containers](#docker-containers):

```yaml
jobs:
  whoami:
    runs-on: ravion/ee=github-actions/type=sandbox/cpu=auto/memory=auto/disk=auto/id=${{ github.run_id }}-${{ github.run_attempt }}-whoami-${{ strategy.job-index || 0 }}
    steps:
      - run: aws sts get-caller-identity
```

Keep these in mind:

- **IMDSv2 only.** Requests must first get a session token with `PUT /latest/api/token`. IMDSv1 requests, which send no token, get `401 Unauthorized`. Current AWS CLI and SDK versions use IMDSv2 automatically.
- **No policies by default.** The job role has no IAM policies attached by default. Calls such as `aws sts get-caller-identity` work, but calls that need permissions return `AccessDenied`. For jobs that need AWS access, use [GitHub OIDC](#use-github-oidc).

### Region

The endpoint serves the sandbox host's region and availability zone at the same paths as EC2: `/latest/meta-data/placement/region` and `/latest/meta-data/placement/availability-zone`. SDKs that read their region from instance metadata when none is configured pick it up. These include the AWS CLI, the AWS SDKs for Python (`boto3`), Java and .NET, and the AWS SDK for Rust.

Set `AWS_REGION` yourself when:

- your code uses an SDK that never reads the region from instance metadata, such as the AWS SDKs for Ruby and JavaScript (v3), or the AWS SDK for Go v2 without `config.WithEC2IMDSRegion()`;
- your AWS resources are in a different region from the sandbox host.

Ravion doesn't set `AWS_REGION` for you, so a region in your environment or AWS config file always wins.

## Docker containers

Docker containers in the job get the job's credentials and region from `169.254.169.254` too, with no setup. That includes:

- `services:` containers;
- `container:` jobs;
- `docker run` with the default network;
- `docker compose` stacks;
- any other Docker bridge network.

```yaml
jobs:
  e2e:
    runs-on: ravion/ee=github-actions/type=sandbox/cpu=auto/memory=auto/disk=auto/id=${{ github.run_id }}-${{ github.run_attempt }}-e2e-${{ strategy.job-index || 0 }}
    services:
      app:
        image: ghcr.io/acme/app:latest
        env:
          # The AWS SDK for Ruby doesn't read the region from instance metadata.
          AWS_REGION: us-east-1
    steps:
      - run: docker compose up -d --wait
      - run: npm run test:e2e
```

SDKs inside the containers refresh the credentials as usual, so long-running containers keep working.

Containers reach the endpoint through a small relay inside the microVM. Firecracker's own metadata service answers only the microVM itself. The relay starts before the job's first step, so `services:` containers have credentials as soon as they start. It differs from EC2's metadata service in a few ways:

| Request | Result |
| --- | --- |
| Session token (`PUT /latest/api/token`) | Served |
| `/latest/meta-data/iam/security-credentials/` and the role under it | Served |
| `/latest/meta-data/placement/region` and `/availability-zone` | Served |
| Any other metadata path, such as `instance-id` | `403 Forbidden` |
| A request that doesn't address `169.254.169.254` by IP in its `Host` header | `403 Forbidden` |
| A token request that came through a proxy (`X-Forwarded-For` or `Forwarded`) | `403 Forbidden` |
| A container on an `--internal` network, or with `--network none` | No route, times out |

Containers started with `--network host` share the microVM's network and reach the endpoint directly.

<Warning>
  Every container in the job can read the job role, including third-party images you run as `services:`. That matches EC2 instances with an IMDS hop limit of 2. To keep a container away from the credentials, run it on an `--internal` network or with `--network none`, or give the job role only the permissions the whole job may use.
</Warning>

## Use GitHub OIDC

For roles that depend on the branch, environment or repository, use [GitHub's OpenID Connect provider](https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/configuring-openid-connect-in-amazon-web-services) with [`aws-actions/configure-aws-credentials`](https://github.com/aws-actions/configure-aws-credentials). This works on Ravion runners the same way as on GitHub-hosted runners, and lets you attach exactly the policies the job needs.

```yaml
permissions:
  id-token: write
  contents: read

jobs:
  integration:
    runs-on: ravion/ee=github-actions/type=sandbox/cpu=auto/memory=auto/disk=auto/id=${{ github.run_id }}-${{ github.run_attempt }}-integration-${{ strategy.job-index || 0 }}
    steps:
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::123456789012:role/ci-integration
          aws-region: us-east-1

      - name: Run a container with the OIDC credentials
        run: |
          docker run --rm \
            -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN \
            -e AWS_REGION \
            ghcr.io/acme/app:latest npm run test:integration
```

The action exports the credentials as environment variables for later steps. Those take precedence over the job role from the metadata endpoint. The action also masks the values in the log.

A container only gets the OIDC credentials if you pass them in. Otherwise its SDK finds the job role at the metadata endpoint. To forward them, pass each variable's name only (`-e AWS_ACCESS_KEY_ID`), or write them to an env file for `docker compose`. In a `container:` job, steps already run inside the container, so the action's credentials reach later steps there directly.

`services:` containers start before any step runs, so they can't receive credentials from a step, including OIDC credentials. They get the job role. To run services with an OIDC role, start them with `docker compose` in a step after `configure-aws-credentials`.

OIDC sessions don't refresh inside a container that received them as environment variables. Set `role-duration-seconds` to cover the job.

### Keep keys out of the job log

Values you write into `services.*.env`, `container.env` or a `docker run -e NAME=value` argument can show up in the job log. Masking only covers values GitHub knows are secret.

- Pass credentials with env files, or with `-e NAME` without a value.
- Reference credentials stored as GitHub secrets with `${{ secrets.NAME }}`. GitHub masks them.
- Mask any other value before anything can print it:

  ```bash
  echo "::add-mask::$AWS_SECRET_ACCESS_KEY"
  echo "::add-mask::$AWS_SESSION_TOKEN"
  ```

## Compared with other runners

| Runner | Ambient AWS role | Reachable from Docker containers |
| --- | --- | --- |
| Ravion sandbox | A role per job, served over IMDSv2 with its region | Yes, credentials and region only |
| RunsOn | The EC2 instance role, shared by every job on the stack, over IMDSv2 with hop limit 2 | Yes |
| GitHub-hosted | None. Use GitHub OIDC. | Not applicable |

If you're moving from RunsOn, `services:` and `container:` code that relied on the instance role finds the job role in the same place. The job role has [no policies by default](#how-sandbox-jobs-get-aws-credentials), so give the job the permissions it needs with [GitHub OIDC](#use-github-oidc). Code that reads other instance metadata, such as `instance-id`, gets `403 Forbidden`.
